# CompatLab research notes

**Reviewed:** October 3, 2026  
**Current documents:** [PRD v1.1](../compatlab_product_requirements_v1.1.md) · [Implementation plan](compatlab-build-plan.md)

These notes record sourced facts and their architectural consequences. Limits, timelines, stack choices, and capacity estimates in the plan are design decisions. No runtime benchmark, exploit test, package corpus evaluation, or VPS inspection was performed during planning. Recheck exact releases and flags when pinning the implementation.

| Topic | Verified source finding | Consequence for this project |
|---|---|---|
| Node launch matrix | Node 24 is LTS and 26 is Current on the review date; 26's LTS promotion is scheduled for October 28, 2026. Node 22 reaches end of life April 30, 2027. The project describes an annual release cycle beginning with 27. [Release overview](https://nodejs.org/en/about/previous-releases), [schedule](https://raw.githubusercontent.com/nodejs/Release/main/schedule.json) | Plan the likely launch matrix around 24/26, qualify releases before use, and represent Node versions as a list. Do not label 26 LTS before promotion. |
| CommonJS loading ESM | Node documents synchronous `require(esm)`, with top-level-await limitations. Export resolution depends on ordered conditions and can use direct targets or `node`, not just `require`/`default`/`module-sync`. [Modules](https://nodejs.org/api/modules.html), [packages](https://nodejs.org/api/packages.html) | `type: module` does not establish inapplicability. Use runtime resolution and expose require/TLA failures as observations. |
| Deno npm/native behavior | Deno supports manual `node_modules`, npm compatibility, synchronous ESM loading through require, and Node-API addons subject to its documented permissions/setup. [Node/npm compatibility](https://docs.deno.com/runtime/fundamentals/node/) | Validate one npm-prepared workspace across the matrix. Allow shipped prebuilt addons; scripts and compilation remain excluded workflows. |
| Deno writes and permissions | The run command documents permission, config, lock, node-modules and cache controls. Deno's security model describes runtime permissions. [Run CLI](https://docs.deno.com/runtime/reference/cli/run/), [security](https://docs.deno.com/runtime/fundamentals/security/) | Use `-A` inside the common OS sandbox, manual modules, no lock/config discovery, private writable `DENO_DIR`, and qualified offline flags. A read-only image alone is insufficient configuration. |
| Permission parity | Node explicitly says its permission model is not a security boundary against malicious code. Its controls differ from Deno's; Bun documents its own evolving Node compatibility. [Node permissions](https://nodejs.org/api/permissions.html), [Bun compatibility](https://bun.sh/docs/runtime/nodejs-compat) | Architectural choice: compare ordinary runtime behavior under one OS policy. Default Node permission flags stay off; permission diagnostics become a separate later profile. |
| Result trust | The runtime models do not establish a separate trust boundary between a harness and an imported module in the same process. [Node permissions](https://nodejs.org/api/permissions.html), [Deno security](https://docs.deno.com/runtime/fundamentals/security/) | Inference: separate files and authenticated supervisor submission prevent stdout confusion and unauthorized worker submissions, but cannot establish adversarially honest in-process results. State that limitation. |
| Docker/gVisor integration | gVisor documents Docker's `--runtime=runsc` integration and systrap as a platform without a KVM requirement. Its security guide explains its application-kernel boundary and remaining deployment responsibilities. [Docker quick start](https://gvisor.dev/docs/user_guide/quick_start/docker/), [platforms](https://gvisor.dev/docs/user_guide/platforms/), [security](https://gvisor.dev/docs/architecture_guide/security/) | Use the documented integration through a small TypeScript supervisor. Qualify the Linux host and surrounding controls; avoid a custom containerd integration. |
| Resource and network controls | Docker documents network, mount and resource options. gVisor describes host and sandbox resource accounting. Disabling networking does not disable process creation. [Docker run](https://docs.docker.com/engine/containers/run/), [gVisor resources](https://gvisor.dev/docs/architecture_guide/resources/) | Test guest process/thread limits, total memory, disk/output quotas, and descendant cleanup. Neither a bind mount nor a host PID flag proves all required bounds. |
| Registry metadata size | npm documents abbreviated installation metadata, artifact integrity fields, and full package metadata that can exceed 10 MB. [Registry metadata](https://github.com/npm/registry/blob/main/docs/responses/package-metadata.md) | Prefer abbreviated responses and selected-version endpoints. Make publication time optional; full packuments are not required scan input. |
| Standard npm preparation | `npm ci` uses an existing lock and rejects dependency/lock disagreement. `ignore-scripts` suppresses lifecycle scripts; explicitly invoking script commands is a separate behavior. [npm ci](https://docs.npmjs.com/cli/v11/commands/npm-ci/) | Resolve a lock, inspect sources/integrity, then use `npm ci --ignore-scripts`; forbid explicit script execution. Standard extraction still runs inside a bounded preparation sandbox. |
| Lock contents and identity | npm documents lock fields including resolved sources, integrity, install-script flags, platform restrictions, links and bundled dependencies. [Lock format](https://docs.npmjs.com/cli/v11/configuring-npm/package-lock-json/) | Use the lock for frozen input identity and policy validation. Inference: lock equality alone cannot prove equality of installed bytes across platforms/installers. Share the actual snapshot and record its generation. Native inspection also needs installed manifests/files. |
| npm cache trust | npm describes cacache as integrity-checked and content-addressed, while noting that the cache stores HTTP request data and other package-related data. [npm cache](https://docs.npmjs.com/cli/v11/commands/npm-cache/) | Integrity detects corruption; it does not justify trusting metadata written by another job. Resolve with fresh metadata; qualify shared tarball reuse only for a frozen lock with expected artifact integrity. |
| Registry allowlist | Squid provides request access rules and ACL types for domains, destinations and ports. [http_access](https://www.squid-cache.org/Doc/config/http_access/), [ACLs](https://www.squid-cache.org/Doc/config/acl/) | Use an existing proxy plus enforced network rules. Proxy environment variables alone do not prevent direct connections or private-network access. |
| PostgreSQL queue | PostgreSQL documents `SKIP LOCKED` as useful for queue-like consumers, while noting its inconsistent view is unsuitable for general queries. [SELECT](https://www.postgresql.org/docs/current/sql-select.html) | Use it only for short job-claim transactions; retain leases, retry rules and transactional result acceptance. No broker or notification fanout is required initially. |
| Self-hosted web | Next.js documents self-hosting and coordination concerns across instances. [Self-hosting](https://nextjs.org/docs/app/guides/self-hosting) | Keep report/state truth in PostgreSQL and explicit caches. Poll durable progress initially; preserve invalidation when adding replicas/caching. |
| Authentication choice | Auth.js's own migration guidance recommends Better Auth for new projects and describes ongoing security/critical maintenance for Auth.js. [Auth.js guidance](https://authjs.dev/getting-started/migrate-to-better-auth) | Use Better Auth for P1 maintainer accounts. MVP operator access remains an SSH CLI. |
| GitHub and CI security | GitHub advises selecting App permissions by feature and documents workflow token/action/self-hosted-runner risks. [App permissions](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/choosing-permissions-for-a-github-app), [Actions secure use](https://docs.github.com/en/actions/reference/security/secure-use) | Separate login from repository automation; keep untrusted PR execution away from privileged deployment and production worker secrets. |
| Adjacent tools | Publint checks package publishing/configuration; Are the Types Wrong focuses on package/type resolution. [Publint](https://publint.dev/docs/), [Are the Types Wrong CLI](https://github.com/arethetypeswrong/arethetypeswrong.github.io/blob/main/packages/cli/README.md) | Validate demand for observed runtime loading, native behavior, provenance, and release comparisons. Avoid duplicating a general package linter in the MVP. |

The batching launch count is arithmetic, not a benchmark: two root groups plus two subpath groups across four runtime images means up to **16 initial launches**, before skips or bounded restarts. The benefit and suitable time limits must be measured under runsc.

Implementation qualification remains necessary for shared-snapshot behavior, runtime flags, prebuilt native addons, cache separation, hostile archive containment, resource/egress controls, lease recovery, classification quality, and report usefulness. Those experiments and their acceptance gates are specified in the build plan rather than repeated as another requirements document.
